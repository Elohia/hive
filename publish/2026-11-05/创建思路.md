## 一、开头那段提示词（原文）

> 在我的电脑上，配置好 Pi、DSH、Super-Agent 等开源项目，将它们组合成一个能够主动提供服务的超级智能。首先，充分探索当前系统已经具备的能力，包括各种 CLI、MCP、Skills、浏览器自动化工具，以及本地和云端的 Agent 执行环境。尽可能利用现有的工具生态，把研发、信息检索、文档处理、项目管理、日程管理、沟通协作等能力都集成进来。整个过程中，需要主动调研 GitHub 上最优秀的开源项目，优先复用成熟的技术成果。将调研内容、架构设计、配置方案、依赖资源、工具使用经验等整理保存，做好版本管理，确保整个系统能够持续迭代、方便迁移。接下来，构建一套主动感知机制，定时巡检我的消息、邮件、日历、文档、代码仓库、项目任务等信息源，结合我的个人工作上下文，理解我正在做什么、关注什么、有哪些尚未完成的事情，以及哪些事情值得主动推进。去互联网寻找类似 Multica 的开源项目或成熟方案，在本地构建一个统一的任务中心，将发现的待办事项、潜在问题、项目机会和需要决策的内容梳理出来，统一放进 Inbox。任务中心需要对所有事项进行分类，并建立 L1 到 L5 的自主执行等级。Level 越高，意味着这件事情越容易被 AI 独立推进。* L1：理解和整理信息，提取待办、总结背景。* L2：分析问题，提供建议和执行方案。* L3：能够完成部分工作，生成可交付的中间成果。* L4：能够自主完成大部分工作，关键环节需要人工确认。* L5：能够端到端完成任务，自主验证结果并交付成果。系统需要能够根据任务类型、上下文、工具能力和权限，自动判断哪些事情可以由 AI 推进，哪些事情需要我参与。对于能够自主完成的任务，要主动制定计划、调用工具、执行操作、验证结果，并持续跟进。对于复杂任务，需要自动拆解成多个子任务，交给不同的 Agent 并行处理，同时管理任务之间的依赖关系。另外，设计好 HITL（Human-in-the-loop）机制。涉及重要决策、对外沟通、内容发布、敏感操作等事项，需要先进入 Outbox，等待我的确认。通过消息通知等方式，将需要我决策的内容主动推送给我，并提供必要的背景、建议和可执行选项。获得授权后，再继续推进后续工作。这个系统的建设存在一定的复杂度。你需要充分利用 Codex 等高能力编码 Agent，让它们对整个工程进行系统性的设计和任务拆分，再将具体任务交给独立的子 Agent 处理。能够并行的任务尽可能并行，能够复用的能力尽可能复用。要求整个执行过程不能偷懒，不能只停留在架构设计、生成代码或者 Demo 阶段。要真正把生态能力用起来，必要时自己编写代码，完成真实环境下的集成、测试和验证，确保每个核心模块都能正常工作。整个系统的架构要清晰、简洁、可移植，稳定性要足够强。需要考虑任务持久化、异常恢复、失败重试、权限隔离、数据安全、执行成本和资源管理，保证 Agent 能够长期稳定运行。同时，为整个执行过程建设一套监控看板，能够直观查看 Inbox、Outbox、任务状态、Agent 执行进度、工具调用记录、执行日志、异常信息和最终交付成果。支持调试、任务重试、人工干预和历史回溯。你还需要持续理解和更新我的个人上下文，包括我的工作职责、正在推进的项目、长期目标、技术兴趣、日常习惯和个人偏好。让 Agent 能够基于这些信息主动判断事情的优先级，并发现潜在的工作机会。整个建设过程需要自主完成调研、架构设计、任务拆分、并行开发、集成测试和部署运行。遇到问题主动寻找解决方案，只有真正需要我决策或者授权的事情才来找我。系统建设完成后，还需要通过真实任务进行端到端自测，验证从信息发现、任务识别、自动规划、自主执行、人工确认到成果交付的完整闭环。确保它能够在后台持续运行，真正主动替我完成工作。最终，我希望得到一个能够长期运行、主动感知信息、理解个人上下文、自主发现任务、持续推进工作、交付真实成果的超级智能。我只需要关注目标和关键决策，剩下的事情，尽可能交给 AI 自己完成。

## 二、我怎么读这段话

这段话看着长，其实只有 9 个**可验收**的要求。我先把它们摊平，否则会做成一堆中间态。

| # | 要求 | 验收口径 |
|--:|:--|:--|
| 1 | 组合已有 Agent 生态，不重造 | 至少 4 个 Agent CLI 能被同一套调度调用 |
| 2 | 主动感知 6 类信息源 | 邮箱/git/文档/日历/本机自动化/自检各能出真数据 |
| 3 | 统一任务中心 + Inbox | 一次 scan 能出可读的待办清单 |
| 4 | L1–L5 自主等级 | 同一件事的等级判定可解释、可复议 |
| 5 | HITL / Outbox | 不可逆动作 100% 先请示，批准后能自动续跑 |
| 6 | 持久化 / 恢复 / 重试 / 预算 | 进程被杀能恢复；失败有退避；有花费上限 |
| 7 | 看板 | Inbox/Outbox/任务/日志/执行器/成本/自检七块都能开 |
| 8 | 个人上下文 | 能从真实语料归纳出"正在做什么、卡在哪" |
| 9 | 端到端真自测 | 从发现到交付的闭环跑通，不是 Demo |

第 2 条追加指令把交付形态也钉死了：**这是个 DSH 插件，带左侧栏、看板、自检、自动依赖安装，还要发 GitHub。**
第 3 条追加把用户面扩大：**新用户本机没有 codex/claude 也得能跑。**

## 三、设计思路（七个决定，每个都有代价）

### 1. 等级判定用规则，不用模型

模型判级会飘：同一件事今天 L2 明天 L4，人就失去信任。

所以做成**确定性流水线**：动作意图 → 基准等级 → 不可逆/对外/金额下调 → 历史成功率上调 → 能力闸门 → clamp。
置信度低于 0.6 才让便宜模型兜底一次，且只取**更保守**的那个答案。

代价：规则要维护；好处：同一输入永远同一输出，可解释、可审计。

### 2. 所有状态只有一个 SQLite 库

用 Node 内置 `node:sqlite`，不引第三方 ORM，不立影子状态（JSON 文件、内存缓存都算）。

代价：并发写要自己排队；好处：备份就是复制一个文件，迁移就是搬一个文件，出问题只要看一张表。

### 3. 零运行时依赖

`node:http` 起服务、`node:sqlite` 存储、`node:child_process` 调执行器、看板是零构建静态页。

代价：少了很多顺手的库；好处：`git clone` 完 `node scripts/hive.mjs doctor` 就能跑，不会出现"装依赖装到崩溃"。

### 4. 执行器可换，契约不变

六个执行器共用同一个契约：给 prompt + 工作目录，回 stdout/stderr/退出码/产物路径。

换 Agent 不改上层。所以今天用 dsh，明天换 codex，调度器一行不动。

### 5. 副作用必须过闸

发信、发布、删除、花钱 —— 只能进 Outbox。卡片带背景、建议、2–4 个可执行选项、风险等级、有效期。

这是我给这套系统划的唯一红线：**自主和失控之间，只隔一道闸门。**

### 6. 一切可重放

每个 Run 的 prompt / stdout / stderr / result 落 `data/runs/<id>/`。
出错不用猜，直接翻现场；重试也有原始输入可以复现。

### 7. 先跑真数据，再谈好看

第一版没有堆功能，先让 `scan` 扫出**真的 33 条**事项。看到"xhs-duty 停了 5.9 天"这种真问题之后，功能优先级自然就排出来了。

## 四、建造顺序（为什么是这个顺序）

1. **调研**：找 Multica / DeepSeek Super-agent / OpenDuet 这几条血统，确认"任务中心 + Router/Worker/Watchdog + 审批流"是成熟结构 —— 不发明新架构。
2. **写架构与不变量**：先定 8 条不变量（单库、零依赖、执行器可换、副作用过闸、可重放、幂等、失败不静默、预算护栏）。后面所有代码都被这 8 条约束。
3. **核心层**：config / db / events / log / llm / credentials / 红线守卫。
4. **任务中心**：items / tasks / runs / approvals / events 五张表 + 状态机。
5. **判定与规划**：triage（规则）+ planner（拆 DAG）。
6. **调度**：router / worker / watchdog（租约、退避、车道、崩溃恢复）。
7. **传感器**：六路，各自幂等（`source + source_ref` 去重）。
8. **执行器**：六个，共用契约。
9. **服务端 + 看板**：HTTP API + SSE + 零构建静态页。
10. **测试**：五套，从核心到端到端。
11. **插件化**：包成 DSH 插件（左侧栏 + 自检 + 一键装依赖）。
12. **文档 + 上传 GitHub**：7 篇 docs + README + 迁移指南。

顺序的原则：**每一层都能单独验证，才往上走。**

## 五、并行怎么排的

- 三个子代理分头做：客户端/设置页、看板与 Agent 依赖页、对外文档。
- 我自己守核心：判定、调度、闸门、执行器契约 —— 这几块强耦合，拆开反而互相打脸。
- 并行边界用文件切开（谁写 client.js、谁写 docs、谁写 api.mjs），不在同一个文件上抢。

## 六、踩到的坑（都写进 docs/04-TOOLING.md）

| 坑 | 现象 | 处理 |
|:--|:--|:--|
| codex 上游余额不足 | 执行器 402 | 默认关掉，写明"充值或改 provider 再开" |
| dsh 冷启动 55s | 任务看着像卡住 | 在 config 里写死 `coldStartSec`，看板显示均耗时 |
| shell 执行器全失败 | 24h 3 次 0 成功 | 说明派给它的都是需要判断的活 —— 不是 bug，是分工错 |
| 代理端口 7892 早死了 | 抓取/探测全挂 | 统一走 7890，并在文档里写死这个事实 |
| 看板无 token | 本机可读可控 | 默认只绑 127.0.0.1，远程必须设 token |

## 七、如果重来，我会改三处

1. **先做 Outbox，再做自动执行**。这次顺序反了，导致早期有几次"能跑但我不敢让它跑"。闸门应该是地基，不是收尾。
2. **上下文归纳器提前**。它是判断优先级的眼睛，早一天有它，传感器那六路就能少扫一半噪声。
3. **看板早上线**。看板不是装饰，是调试界面 —— 有它之后定位问题从"翻日志"变成"看一眼"。

## 八、这套思路能复用到哪

同样的骨架（感知 → 判定 → 派活 → 闸门 → 台账），换个领域就能长成别的系统：

- 内容运营：扫平台 → 判选题 → 派写稿 → 人审 → 发
- 交付：扫订单/邮件 → 判等级 → 派执行 → 人确认收款 → 交付
- 运维：扫告警/日志 → 判严重度 → 派修复 → 人批高危 → 复盘

变的是传感器和执行器，不变的是**等级判定 + 闸门 + 台账**这三件。
