# 它攒了 45 条待办，一条都没执行。

（文章草稿 · 2026-11-07 · 全文约 1450 字 · 图：01-收件箱堆积 / 02-收敛前后 / 03-判官概率）

---

两天前我把 HIVE 发出去时，说它「会主动找活干」。今天打开看板，收件箱 45 条，最老的躺了 1 天 18 小时，对应任务数：0。

不是它偷懒。是它在很努力地**假装工作**，而我没看出来。

下面是三个我踩到的真坑。都是"看起来一切正常、其实什么都没发生"的那种。

## 一、一分钟跑了 14 次同一个判定

插件内我写了个 3 秒一跳的调度循环：`setInterval(() => tick(), 3000)`。

`tick()` 是 async 的，我一贯不 await —— 反正下一跳会接着跑。

问题是一轮判定要调好几次模型，耗时以分钟计。3 秒起一跳，上一跳还没完就起了下一跳。翻了事件日志：

```
13:37:44 triage 判定 15 项
13:37:53 triage 判定 15 项
13:38:01 triage 判定 15 项
13:38:05 triage 判定 15 项
13:38:10 triage 判定 15 项 ×2
```

一分钟 14 次。十几轮并发，抢的是**我自己在用的那个模型服务**。

症状不是报错，是「我切会话时对话变卡、HIVE 看着像掉线」。我甚至还去查了宿主的连接状态、查了插件路由，一通排查——查的方向全错。

修法很简单：一个互斥锁，加把 `setInterval` 改成自续期 `setTimeout`（跑完再排下一拍）。三行。

教训：**并发不报错，它只是变慢**。而"变慢"的症状会把你指向完全错误的地方。

## 二、我让一个 0.5B 模型当判官

系统要给每件事判 L1–L5 的自主等级。我嫌调用大模型贵，本机有个现成的 `jevlocal-0.5b`（决策模型的本地复现，RTX2060 上热点 300–800ms，零 token 成本）。

它的文档写着：英文 choice/noul 可用（sst2 85% / agnews 68%），置信带分离优秀（高带 acc 88% / 低带 5%）。

听起来正合适。我接进去，还专门设计了「它够确信就用它的、不够就交回大模型」的闸门。

然后拿真实事项打：

```
L1–L5 五档：      topProb 0.28 / 0.31 / 0.36   ← 基线 1/5 = 0.2
噪音判定(noul)： 退信 0.500 / 营销 0.608 / 真实合同 0.637
是否外部动作：    0.569 / 0.657 / 0.672
```

三类东西挤在同一个数上，**分不开**。五档分布近似均匀，等于没信息。

sst2 的 85% 是**影评情感**——具体、二元、同分布。我拿它判"这封邮件要不要处理"，是彻底的 out-of-distribution。

代码我留着，但默认关掉了。注释里写的是：

> 实测它对本项目的判定没有判别力。代码保留是为了防止后人再踩；英文二元任务可直接复用。

顺手还抓到两个更隐蔽的 bug：

**bug 1**：那个置信度 `confidence = 1 − H(p)/lnK`，K 是**选项数**。五档判定的上限只有 0.24（最确定的情况下 p=[0.6,.1,.1,.1,.1] 也只有 0.237）。我拿 0.55 当阈值——**永远不可能达标**。

**bug 2**：规则层的置信度是 `0.55 + 命中数 × 0.08`。1 处关键词命中就给 0.63–0.71。「置信 < 0.6 才让大模型兜底」这个闸门，**几乎从不触发**。

也就是说：我以为有个大模型在兜底，实际上它一次都没上过场。

## 三、只进不出

最要命的是这个，而且它是我**当初主动写进设计**的。

系统里有个字段叫 `kind='fyi'`——纯情报，判定完只留档、不派活。当时的注释是这么写的：

> 守中：fyi 不派活、不花 token，只留在 Inbox 当背景信息。

听起来很合理。但我的六路传感器里，文档那一路扫的是 `D:\pi-agent\reports`——那个项目每天产出 30 到 50 份报告。**每一份都是一个 fyi**。90% 的入库都是 fyi。

于是：判定跑了、结论写了、状态没变、永久占位。

41 条里：读档 23 条、低优先级归档 17 条、真需要处理 1 条。再加上另外两处：

- 优先级低于阈值的项，判为 `quiet` 后**只 `continue`**，不落状态，每轮重新遍历
- 遍历按 `priority DESC` 取前 60 条，名额被同一批高优先级占满，12 条未判定的**永远轮到**

还有一个更隐蔽的：`bucket` 和 `status` 是两个维度。我归档时只改了 `status='archived'`，可 KPI 数的是 `bucket='inbox'`——**归档完看板照样显示 41 条**。

## 四、修完之后的数字

加了四档收敛规则（重复折叠、过期情报 1 天、通用老化 3 天、容量上限 60 条），每个动作都写事件、只归档不删除。

真实库实跑：

```
第一轮：41 → 21    （20 条 fyi 读档）
第二轮：21 →  1    （3 条读档 + 17 条低优先级归档）
今日花费：¥0.0000
```

**一分钱没花**。清库存没走模型——因为该走模型的都不是库存。

最终：待办只剩个位数、已完成 65、已归档 21。

## 五、三个可以带走的判断

**一、主动性系统的失败模式，是"安静"。**

它不会崩，不会报错，只是慢慢不出活。所以监控的不是正确率，是**吞吐**：这一轮进来了多少、出去多少。只进不出就是故障，哪怕每一步都"成功"。

**二、并发不报错，只变慢。而"变慢"会把你指向错误的方向。**

我花了半小时查连接和路由，真正的问题在一个没 await 的 `setInterval` 里。

**三、用一个小模型省钱，前提是它的能力边界真的覆盖你的任务。**

同一个模型在 sst2 上 85%，在我这里的分布近似均匀。**换个题型就是换了个模型**。要接就得先测，测的方法还得和真实用例同分布——否则你得到的是一个永远不触发的闸门。
